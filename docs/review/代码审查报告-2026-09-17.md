## 二、🔴 阻断级（已修）

### 1. R5 服务层权限：新增的 `IO点位服务.异步新增一栏` 只在界面校验

位置：`src/PlcHmi.Business/Services/IoPointService.cs`

**为什么是阻断级**：审查标准 R5 原文 —— *"写操作在**服务层**经 `权限守卫接口` 校验 →
**只在 ViewModel 校验 = 🔴**"*。而 `docs/07` 记录了 2026-09-13 的一次系统性整改：
**全部 7 处权限检查曾都只在 ViewModel，服务层一处都没有**，当时已补上
`延时/按钮表`、`报警定义`、`手动页元件`、`轴地址`、`PLC 连接参数`、`示教写入`、`切机种`、`参数下发`。

本次新增的"新增 IO 点位一栏"**写的是 `io-points.json` 并改变采集范围**，
危险度与"改 PLC 连接"同级（代码注释自己也这么写），却只在 `IO视图模型.刷新权限` 里把按钮置灰。
绕过界面的成本极低：任何持有 `IO点位服务接口` 的代码、将来的 Web 接口、或一个忘了隐藏按钮的新页面，
都能直接改采集范围。**同一个坑第二次踩**，所以按阻断处理。

**修法**：
- `IO点位服务` 注入 `权限守卫接口`，且**刻意不给默认值**（"缺少守卫时默认放行"正是 R5 要拦的失效模式），
  并在构造期 `ArgumentNullException.ThrowIfNull`。
- `异步新增一栏` 首行 `_权限.要求(权限.编辑IO点位)`，早于取侧、算编号与任何状态变更 —— 被拒的调用不留痕迹。

**验证**：新增 `IO点位新增一栏测试.无权限新增一栏应被拒绝且不改动点位表`
（走**生产用的真实守卫** `用户权限守卫`，未登录即操作员），断言抛 `UnauthorizedAccessException`
且点位表与元数据均未变。

## 三、🟡 建议级

### 3. R2 线程与 UI：运行页「当前节拍」缺少初始快照（已修）

位置：`src/PlcHmi.App/ViewModels/RunViewModel.cs:58`

**为什么提**：`设备服务` 只在**值发生变化**（`Math.Abs(差值) > 1e-6`）时才触发 `周期时间已变更`。
`运行视图模型` 构造期只拉了 `状态` 与 `报警摘要` 的快照，`异步初始化` 只补了产量 ——
`应用周期时间` **只在事件处理器里被调用**。若 HMI 在机器以恒定节拍生产时启动，
事件永远不来，「当前节拍」会一直停在 `--.---`。
审查清单 R2 原文：*"漏掉会表现为'启动后界面空白，等到下一次状态变化才刷新' → 🟡"*。

**修法**：`异步初始化` 主动拉一次 `_设备.周期时间秒`（同时覆盖切页返回的场景）。

### 4. R1 地址与字序：轴参数区**内部**的 PLC 自有字段没有任何保护（已修）

位置：`src/PlcHmi.Business/Services/AxisAddressService.cs` → `AxisAddressValidator.cs`

**为什么提**：`参数地址范围` 只校验"D 区且落在 D1200–D1799"，是**粗粒度**的。
而按现场 PLC 地址分配表（`docs/01` §十、`docs/02` §2.1），该区间内部被 PLC 按固定偏移切分：
偏移 0 点动速度 / 4 加减速度 / 10 命令字 / 11 定位点字 / 20 轴状态字 / 23 轴故障码。
**管理员把「点动档位」填成 D1220 能通过区间校验**，之后每写一次档位就覆盖一次轴状态字 ——
界面上的轴状态会莫名跳动，现场极难联想到"改的是档位地址"。既有的重叠检查也拦不住：
D1220 与 `AxisXPosition`(D1221) 不重叠。

**修法**：`轴地址校验器.检查轴参数区内部` 按**所属轴块**（`(地址-1200)/100`）计算偏移，
命中 PLC 自有字段即拒绝，错误文案直接给出字段名与建议。
偏移 10（命令字）标为「允许字内位」—— 点动方向本来就写在它的第 2/3 位，
若一并拦掉，**默认配置自己就过不了校验**（这是最容易做成假阳性的地方）。
不用轴名推块号，而是从地址反推块起点，避免轴顺序变化时错位。

**验证**：新增 `轴参数区内的PLC自有字段应被拒绝`（6 例，含轴 2 的 D1320，专门验"偏移必须按轴块算"）
+ `命令字内的空闲位仍应被接受`（防假阳性）。

### 5. 配置静默降级：变量表同字多位被无声丢弃（已修）

位置：`src/PlcHmi.Business/Services/VariableTableService.cs:104`

**为什么提**：D 字内位可寻址后，同一字上的第 2 个及以后的变量会被 `continue` 跳过 ——
这是**正确的设计**（Modbus/OPC UA 侧读写的是整字，反查只能回到一个字），
但**一行日志都没有**。项目自己的原则是"配置静默降级成少了一半绑定，比崩溃更难查"。
一个导入 16 位命令字的变量表会丢掉 15 个变量的地址反查，现场只会表现为"某些点位读不到值"。

**修法**：聚合为一条 Warning，列出被遮蔽的条目（最多 8 个）并说明"按变量名绑定不受影响"。
不做逐条日志 —— 那会在导入时报出十几条噪音。

### 6. 位寻址在 OPC UA 模式下语义完整（**未修，转跟踪项**）

位置：`src/PlcHmi.Communication/OpcUa/NodeIdResolver.cs:47,78`

**为什么提**：`NodeId推导器` 的缓存键与 NodeId 文本都只含 `(区域, Modbus 地址)`，
不含位序号 —— `D1210.2` 与 `D1210.3` 会推导出**同一个** NodeId `ns=2;s=D1210`。
当前靠 `TagWriter` 对字内位统一走"读整字 → 改位 → 写整字"因而**语义自洽**
（两条路径读写的都是整字节点）；但如果 OPC UA 服务端把位暴露成**独立 Bool 节点**
（汇川变量表的典型做法），则整字节点可能不存在 → 读失败 → **点动失效**，
而点动是"按住才动、松开即停"的安全出口。

**为什么没修**：无法在无服务端的情况下判定节点组织方式，凭猜改反而会引入新缺陷。
**跟踪项**：与 PLC 侧确认 D 字内位在 OPC UA 地址空间中是整字节点还是独立 Bool 节点；
无论哪种，都应给 `NodeId推导器` 补一条字内位的显式测试。

### 7. 💭 注释与 `docs/01` 的口径差一句限定

`src/PlcHmi.Core/Models/RecipeConfigParts.cs` 的地址分区注释写
"D2500–D3499 为默认机种配方区"，而 `docs/01` 的同一行还有关键限定
**"与示教点表区重叠段现由示教与机种控制使用"**。少了这半句，后来者按注释把配方参数放到 D2500
就会撞掉示教点表（X 轴基址正是 2500）。建议补上限定语。

## 四、💭 细节

| 项 | 说明 |
|---|---|
| `TagWriter.字位写锁` 是 `static SemaphoreSlim` | 跨所有客户端实例串行化（Modbus 与 OPC UA 并存时会互相等待），且从不释放。当前单连接设计下无害，多连接时会变成不必要的瓶颈 |
| `IoViewModel.异步新增一栏` 直接读 `表格.元.分组大小` | 服务层有 `分组大小() => 值 > 0 ? 值 : 8` 的 0 兜底，界面侧没有。配置里分组大小为 0 时，确认框会显示 "0 点"、预览会算出负编号 |
| `IO视图模型.异步新增一栏` 的 `预览` 与实算各一次 | 两次之间若表被改动，提示文案与实际结果可能不一致（当前单用户场景下不会发生） |
