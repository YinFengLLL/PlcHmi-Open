# 04 · 代码审查标准与流程

> 版本 v1.0 ／ 2026-09-10
> 适用项目：PlcHmi（WPF 工控上位机模板）
> 一句话原则：**审查的目的不是挑刺，而是在缺陷到达现场设备之前把它拦住。**

---

## 0. 为什么工控上位机的审查标准必须比一般业务系统更严

普通 Web 应用的 Bug 代价是报错页、重试、用户投诉。
本项目的 Bug 代价可能是：**轴撞到原点以外的位置、气缸乱动、产品报废、人员受伤。**

因此本项目采用**双轨清单**：

| 轨道 | 关注点 | 谁最懂 |
|---|---|---|
| **通用五线** | 正确性 / 安全 / 可维护 / 性能 / 测试 | 任何有经验的 C# 工程师 |
| **工控红线** | 地址与字序 / 线程与 UI / 数据落盘 / PLC 交互 / 权限 / 配置化 | 只有熟悉这台设备和这套代码约定的人 |

**通用五线防的是"代码坏"，工控红线防的是"设备坏"。两条都得过。**

### 1.1 立刻能抓到的两个真实缺陷（示范审查格式）

> ⚠️ 本节示例代码中的标识符为 **2026-09-10 当时的英文名**。
> 全部自研标识符已于 2026-09-14 中文化（如 `RecipeStore`→`配方存储`、`UserFile`→`用户文件`），
> 示例保留原名是为了忠实记录当时的审查现场。规则与风格现状见
> `docs/08-标识符中文化改造与坑点.md`。

下面这两条不是假想，是刚才从代码里读出来的。用它们演示本标准的输出长什么样。

```
🔴 **数据完整性：recipes.json 写入不是原子的**
位置：src/PlcHmi.Business/Services/RecipeStore.cs:129

    await File.WriteAllTextAsync(ConfigPaths.Recipes, json, cancellationToken);

**为什么是阻断级：** File.WriteAllTextAsync 会先截断文件再写入。
若此刻断电、进程被杀、或磁盘写满，recipes.json 会停在"已被截断、尚未写完"的中间态——
下次启动 Load() 反序列化失败 → 走 catch 分支 → **全部 20 个机种的参数与点表清空**。
现场表现是"开机后配方全没了"，而且不可恢复。

**建议：** 写临时文件 → 原子替换，替换前先备份：

    var tmp = ConfigPaths.Recipes + ".tmp";
    await File.WriteAllTextAsync(tmp, json, cancellationToken).ConfigureAwait(false);
    File.Move(tmp, ConfigPaths.Recipes, overwrite: true);   // 同卷内 Move 是原子操作
    // 可选：保留一份 recipes.json.bak 用于回滚

**同类问题：** 其余 19 处文件写入应一并排查（users.json / alarms.json / param-tables.json 等）。
```

```
🟡 **线程纪律：异步方法里调用了同步阻塞 API（静态分析实测 4 处）**
位置：
  src/PlcHmi.Business/Services/AlarmDefinitionService.cs:74
  src/PlcHmi.Business/Services/ManualWidgetService.cs:54
  src/PlcHmi.Business/Services/ParamTableService.cs:76
  src/PlcHmi.Business/Services/UserService.cs:87

    using var stream = File.OpenRead(path);
    var loaded = JsonSerializer.Deserialize<UserFile>(stream, JsonConfig.Read);  // ← 同步重载

**为什么提：** 所在方法本身是 `async`（`LoadAsync`），却调用了同步版 `Deserialize`。
按项目自己的红线 R2，异步路径里不应出现同步阻塞调用 —— 这类写法正是"界面偶尔卡一下"的典型来源。

**影响评估（诚实地说）：** 这 4 个文件都是几百字节到几 KB 的本地配置，
实际阻塞时间在微秒级，**不构成线上故障**。列为 🟡 而不是 🔴，是出于这个判断。
但代码一旦被复制到读大文件或走网络的场景，就会变成真问题 —— 所以值得现在统一。

**建议：** 改用异步重载（属于机械替换，风险极低）：

    var loaded = await JsonSerializer.DeserializeAsync<UserFile>(stream, JsonConfig.Read, cancellationToken)
                                .ConfigureAwait(false);

**跟踪：** 修完这 4 处后，可把 `.editorconfig` 里 `CA1849` 提升为 `warning` 纳入门禁。
```

```
🟡 **资源释放：测试中 3 处 `VirtualPlcDevice` 未释放**
位置：src/PlcHmi.Tests/DeviceStatusAndSimulationTests.cs:41, 51, 65

    var device = new VirtualPlcDevice(NullLogger<VirtualPlcDevice>.Instance);
    // ... 测试结束，没有 Dispose

**为什么提：** `VirtualPlcDevice` 实现了 `IDisposable`。测试里不释放，
在多测试并行（xUnit 默认同一 collection 内串行、跨 collection 并行）时可能互相干扰，
表现为"本地单跑都过、全量跑偶尔挂"这种最难查的间歇性失败。

**建议：** 改为 `using var device = new VirtualPlcDevice(...);`。
```

```
🟡 **可维护性：单文件行数超过审查阈值**
位置：src/PlcHmi.Business/Services/TeachService.cs（574 行）

**为什么提：** 400 行以上的文件，审查者很难在心里维持完整上下文，
回归缺陷极易漏过。实测 8 个文件越线，`TeachService` 最严重。

**建议：** 不要求立刻重构（能跑就别乱动），但**新增功能不要再往这些文件里塞**。
下次改动 `TeachService` 时，顺手把「点表编解码」与「PLC 读写」拆成两个类。
```

## 2. 严重度分级（团队统一语言）

所有审查意见必须带标记，避免"你觉得严重我觉得无所谓"的扯皮。

| 标记 | 名称 | 定义 | 处理要求 |
|---|---|---|---|
| 🔴 | **Blocker 阻断** | 会导致**数据丢失、设备异常动作、安全漏洞、死锁、崩溃**，或**破坏既有契约** | **必须修复后才能合入**，无例外、无"下个版本再说" |
| 🟡 | **Suggestion 建议** | 正确但不健壮：缺输入校验、缺测试、命名费解、性能隐患、重复代码 | **原则上本次修复**；若有正当理由可延后，但必须在 PR 里写明理由与跟踪项 |
| 💭 | **Nit 细节** | 风格、文案、注释、可读性、替代写法 | **不阻塞合入**；作者可自行决定，也可直接忽略 |

> **纪律：** 审查者不得用 🔴 表达个人偏好。"我不喜欢这种写法"只能是 💭。
> **反向纪律：** 作者不得把 🔴 降级为由主管裁决的争议 —— 🔴 清单在 §3.2 有明确判定标准。

## 3. 审查清单

### 3.1 通用五线（每次审查都要过一遍）

**① 正确性**
- [ ] 逻辑是否覆盖了题目要求的所有分支？边界值（0 / 空 / 最大索引 99 / 负数坐标）如何？
- [ ] 循环边界是 `<=` 还是 `<`？索引偏移 ±1 是否对？（本项目 0–99 索引极易写错）
- [ ] `null` / 默认值路径是否处理？`Nullable` 已开，编译器警告即线索。
- [ ] 异常路径：失败时是抛异常、返回默认值，还是静默继续？**关键路径不允许静默继续。**

**② 安全**
- [ ] 所有外部输入（JSON 配置、用户输入框、CSV 导入、来自 PLC 的原始数据）是否校验范围与格式？
- [ ] 权限检查是否落在**服务层**，而非只靠界面置灰？（界面绕过成本极低）
- [ ] 有无把密码/密钥/连接串写进日志或异常消息？
- [ ] 反序列化是否用了 `JsonSerializerOptions` 白名单？（现有 `JSON配置.读取` 已统一，勿绕过）

**③ 可维护性**
- [ ] 命名是否表达了意图？能不能删掉注释后仍读懂？
- [ ] **标识符是否符合中文命名规范**（见 §3.4）？英文只允许出现在框架约定成员与领域专名例外清单里 → 违反 = 🟡
- [ ] 文件是否超过 400 行？函数是否超过 50 行？超了就说明职责该拆。
- [ ] 有无重复逻辑该抽成公共方法？（同类代码出现第 3 次就该抽）
- [ ] 魔法数字是否已具名？（`2500`、`2700`、`0.005`、`500` 这类必须具名或来自配置）

**④ 性能**
- [ ] 有无在轮询循环 / 定时器回调里做分配、字符串拼接、LINQ 多次枚举？
- [ ] 有无 N+1 式的逐点 Modbus 请求？（本项目一次请求可读多个寄存器，逐点读是典型浪费）
- [ ] UI 线程上是否做了 CPU 密集或阻塞 I/O 操作？

**⑤ 测试**
- [ ] 新增/修改的核心逻辑是否有对应测试？
- [ ] 测试是否覆盖了**失败路径**，而不只覆盖 happy path？
- [ ] 测试命名能否看出"什么条件下期望什么结果"？（本项目用中文命名，是优点，继续保持）
- [ ] 有没有为了跑通测试而改断言、或把 `Assert` 删掉的痕迹？（🔴 一经发现按阻断处理）

### 3.2 工控红线（本项目专属，🔴 判定标准）

**R1 · 地址与字序 —— 错一个字节，轴就跑到别的地方**

- [ ] 新增/修改的任何软元件地址，是否落在 `recipe-config.json` 声明的合法区间内？
      参数地址改动**只允许 D1200–D1799**（2026-09-17 按 PLC 地址分配表更新）。
- [ ] 是否**绕过 `寄存器编解码器` 手写了字序拆分**？ → 🔴 **禁止**。32 位整型与 float32 共用同一套 CDAB 规则。
- [ ] 涉及 32 位值编解码的改动，是否附带了**实测向量单测**？
      （120.00 → `0x0000,0x42F0`；9999.99 → `0x3FF6,0x461C`）
      没有向量测试的编解码改动 = 🔴，因为字序写反的症状是"120 读成 0"，现场极难定位。
- [ ] 坐标比较是否用了**容差 0.005**？用 `==` 比较 float → 🔴。
- [ ] 示教点读写是否**按轴分区**（4 次请求 × 20 字）？写成"一面 80 字连续读" → 🔴（会读到跨轴脏数据）。
- [ ] 报警源是否只在 **M500–M600**（`Bit=-1`，走 **FC01 读线圈**）或 **D550–D554**（`Bit=0..15`，走 **FC03 读寄存器**）？
      混用功能码 / 越界地址 → 🔴。

**R2 · 线程与 UI —— 死锁和界面冻结的主要来源**

- [ ] UI 线程切换是否用 `BeginInvoke`？出现 `Invoke` → 🔴（后台线程同步阻塞，与 UI 线程等后台互锁即死锁）。
- [ ] 是否用了 `SemaphoreSlim.Wait()`？ → 🔴，一律 `await WaitAsync()`。
- [ ] CPU 密集计算（哈希、大数组编解码、CSV 生成）是否 `Task.Run` 移出 UI 线程？没移 → 🟡（界面卡顿，可感知）。
- [ ] 新增 `async void` 是否**仅限事件处理器**且**自带 try/catch 兜底**？其他场景 `async void` → 🔴（异常无法捕获，直接崩进程）。
- [ ] 新增后台服务是否实现 `IDisposable` / `IAsyncDisposable`，并接受 `CancellationToken`？
      **退出时未取消的定时器 = 进程无法干净退出 → 🟡**。
- [ ] 只订阅事件流的服务，是否在构造函数**主动拉一次快照**？
      漏掉会表现为"启动后界面空白，等到下一次状态变化才刷新" → 🟡。

**R3 · 数据落盘 —— 停电一次就损失配方，是不可接受的风险**

- [ ] 写文件是否**原子**（写 `.tmp` → `File.Move(overwrite:true)`）？直接 `File.WriteAllText` → 🟡，若写的是 `recipes.json`/`users.json` → 🔴。
- [ ] `recipes.json` 的写入是否**统一经 `配方存储`**？
      谁另建了一份内存副本 → 🔴（典型"单机双写"陷阱：后保存者覆盖先保存者）。
- [ ] 参数是否**只在** `异步写入参数` / `异步切换` 落 PLC？示教点是否**只在** `异步示教` / `异步写入面` 落 PLC？
      在输入框 `TextChanged` 里直接下发的改动 → 🔴（每敲一个字符就写一次 PLC）。
- [ ] 未启用面是否在**服务层**拦截（抛 `InvalidOperationException`）？只靠界面置灰 → 🟡。
- [ ] 面启用默认值是否为 `false`？默认为 `true` → 🔴（空点会把轴驱动到原点）。

**R4 · PLC 交互 —— 上位机永远不越权**

- [ ] PLC 状态字映射是否经 `设备服务.映射状态字()`？直接 `(设备状态)raw` 强转 → 🔴
      （PLC 约定 `0=空闲中 1=运行中 2=待机中 3=复位中 4=报警中`，C# `设备状态.未知=0`，强转语义完全错位）。
- [ ] 手动页/点动是否**只置位 M 区**？直接写 Y 输出 → 🔴（绕过 PLC 联锁，可能撞机）。
- [ ] 常闭输入点是否在 `io-points.json` 标了 `inverted: true`？漏标 → 🟡（状态显示反相，误导操作员）。
- [ ] 写命令是否走**串行队列**？并发写 PLC → 🟡（寄存器撕裂）。
- [ ] 断线重连是否有退避策略，且**不吞掉**连接异常？静默重试无日志 → 🟡。

**R5 · 权限与配置化 —— 让换设备不用改代码**

- [ ] 新增的每个写操作/命令，是否声明了所需权限？未声明 → 🟡，若是管理员专有功能（延时表 / 按钮表 / 报警编辑 / 元件编辑）→ 🔴。
- [ ] 权限是否在**服务层**再校验一次？（界面隐藏按钮不算保护）
- [ ] 新增点位 / 报警 / 元件的定义，是否放进了对应的 JSON 而不是硬编码在 C# 里？硬编码 → 🟡。
- [ ] XAML 中新增的 `{StaticResource X}`，键名是否确实存在于 `Themes/*.xaml`？
      写错不会立刻报错，但打开该对话框即崩 → 🔴。（`--smoke` 会实例化全部对话框，跑一遍即可拦下）

### 3.3 阈值速查（一页纸）

| 指标 | 阈值 | 超限处理 |
|---|---|---|
| 单文件行数 | 400 | 新增代码禁止再进；改动时顺手拆 |
| 单函数行数 | 50 | 拆方法 |
| 方法参数个数 | 5 | 引入参数对象 |
| `catch (Exception)` | — | 必须 `Log` + 有兜底；纯吞掉为 🔴 |
| 嵌套深度 | 3 层 | 提前 return / 提取方法 |
| TODO 遗留 | 0 | 每个 TODO 必须带负责人与日期 |

### 3.4 标识符命名规范（2026-09-14 起永久生效）

> 自 2026-09-14 起，本项目自研代码的标识符**一律使用中文**（背景与坑点见
> `docs/08-标识符中文化改造与坑点.md`）。审查时按此节判定。

**风格规则**

| 对象 | 风格 | 示例 |
|---|---|---|
| 类型 / 方法 / 属性 / 事件 | 中文名词或动宾短语，不加空格 | `报警扫描服务`、`异步写入参数`、`连接状态文本` |
| 字段 / 局部变量 / 参数 | 中文名词 | `标签集合`、`当前用户` |
| 私有字段 | 下划线前缀 | `_连接状态文本` |
| 布尔值 | `是否…` / `有…` / `可…` 开头 | `是否启用`、`可编辑元件` |
| 集合 | `…列表` / `…集合` / `…表格` | `延迟集合` |
| [ObservableProperty] | `_中文名` 字段 → 生成属性 `中文名` | `_是否选中` → `是否选中` |

**英文例外清单（允许保留英文的位置，审查不得判 🟡）**

1. **框架约定成员**：override / 接口实现 / 事件处理器签名
   （`OnStartup`、`Dispose`、`StartAsync`、`Convert`…）—— 改名即破坏契约。
2. **源生成器钩子参数**：`partial void On是否选中Changed(bool value)` 的 `value` 必须与生成声明同名。
3. **领域专名**：`PLC`、`CSV`、`JSON`、`Modbus`、`汇川` 等行业通名可出现在中文标识符内部。
4. **设备约定名**：与 PLC 图纸、配置 JSON 一一对应的枚举成员
   （`软元素.X/M/SM`、`标签数据类型.UInt16`、`轴标识.X`…）—— **禁止改译**。
5. **文件名 / 项目名 / XAML 资源键**：不在中文化范围（`RecipeStore.cs`、`ButtonSuccess` 保持原名）。

**改名类改动的红线**（改名 = 跨文件契约变更）：

- 改属性名 → 同步 `config/*.json` 键；漏改 = 🔴（配置静默降级为空数据）
- 改枚举成员 → 全库搜该枚举的字符串用法（JSON / XAML / 日志文案）；漏改 = 🔴
- 改命令 / 属性名 → 同步 XAML 绑定路径；漏改 = 🔴（编译测试全绿但界面是死的）
- 改名后新增 lambda 参数与外围变量同名 → 🟡（语义漂移温床）

## 4. 审查流程

### 4.1 前置条件（**必须先补，否则后面全是空话**）

| 顺序 | 事项 | 理由 |
|---|---|---|
| **1** | `git init`，提交当前全部代码作为基线，加 `.gitignore`（排除 `obj/ bin/ dist/ publish/ logs/`） | **没有版本控制就没有 diff，没有 diff 就没有审查。** 这是唯一的先决条件 |
| 2 | 落 `.editorconfig`（见配套文件） | 让格式争议由工具解决，人只审逻辑 |
| 3 | 建立 `main`（受保护）+ `feature/*` 分支模型 | 提供审查的物理载体 |

> ⚠️ 提醒：仓库目前**无任何备份**。历史上已因此丢失过 2 篇文档（见项目记忆"血的教训"）。
> 在 `git init` + 首次提交完成之前，任何重构都有不可恢复的风险。

### 4.2 分级审查（不是所有改动都值得同等投入）

| 等级 | 触发条件 | 审查方式 | 硬性验证 |
|---|---|---|---|
| **L1 轻量** | 注释、文案、样式、局部 XAML 微调；不改逻辑 | 1 人审 | build 通过 |
| **L2 标准** | 业务逻辑、服务层、ViewModel、新增配置项 | 1 人审 | build + test + 新增测试 |
| **L3 重度** | **通信层 / 地址映射 / 编解码 / 权限 / 落盘策略 / 数据库或配置文件格式变更** | **2 人审（至少 1 人熟悉 PLC 侧）** | build + test + `--smoke` + **模拟器或真机验证** |

> L3 是本项目的重点。**碰地址、碰字序、碰权限、碰落盘的改动，一律 L3。**

### 4.3 角色分工

**提交者（作者）—— 先自检，再请人看**

1. 本地跑通 §5 的全部门禁命令，**红灯不提交**。
2. 自填 PR 描述（模板见 `docs/review/PR模板.md`），必须写清：**改了什么 / 为什么改 / 怎么验证的 / 影响哪些地址或权限**。
3. 对 L3 改动，主动标注"请重点看字序/权限/落盘"。

**审查者 —— 只审清单里的东西**

1. 先看 PR 描述与 diff 范围，建立意图，再逐行读。
2. **必须先给整体印象**（做得好在哪、主要风险在哪），再给逐条意见。
3. 每条意见使用 §2 的标记 + §5 模板的格式（位置 / 为什么 / 建议）。
4. **一次性给完**，不要挤牙膏式分多轮。
5. **不确定就问**："这里我理解是 X，是故意的吗？" —— 而不是直接判定为错。
6. **看到好代码要说出来**。这是团队愿意继续做审查的关键。

### 4.4 合入条件（Definition of Done）

一次改动可以合入，当且仅当：

- [ ] `dotnet build PlcHmi.slnx -warnaserror --no-incremental` → **0 警告 0 错误**
      （`--no-incremental` 必须带：增量编译会跳过未改动项目，门禁会假绿）
- [ ] `dotnet test PlcHmi.slnx` → **全部通过**（当前基线 **406** 个）
- [ ] 涉及 UI 的改动：`PlcHmi.App.exe --smoke` → 8 页 + **4** 对话框全过
- [ ] 涉及地址 / 编解码：**有实测向量单测**
- [ ] 所有审查意见已解决，或已明确降级并**留下跟踪项**
- [ ] **无未解决的 🔴**

### 4.5 分歧怎么处理

1. 回到 §3 清单原文，先讨论"这属于哪一条"。
2. 清单未覆盖的 → 记录为新增条目候选，本次按 🟡 处理（**不要为规则外的争论拖住合入**）。
3. 仍然分歧 → 由了解现场设备的一方裁决（工控领域，**设备安全 > 代码洁癖**）。

## 5. 自动化门禁（把能自动化的都自动化）

人眼只应该看机器看不出的东西（意图、设计、边界）。下面这些**不许靠自觉**。

### 5.1 本地一条命令搞定

建议新增 `tools/verify.sh`（或 `.cmd`），把门禁串成一步：

```bash
#!/usr/bin/env bash
# 提交前自检门禁 —— 任何一步红灯都不许提 PR
set -e
source ~/.workbuddy/dotnet-env.sh   # 沙箱/CI 环境必需，否则 NuGet 报 path1
cd "$(dirname "$0")/.."

echo "==> 1/3 构建（要求 0 警告 0 错误）"
dotnet build PlcHmi.slnx -warnaserror

echo "==> 2/3 测试"
dotnet test PlcHmi.slnx --no-build

echo "==> 3/3 界面自检（8 页 + 3 对话框）"
./src/PlcHmi.App/bin/Debug/net10.0-windows/PlcHmi.App.exe --smoke || true
# 注意：--smoke 失败会返回非 0，此处按实际路径与退出码调整为硬门禁

echo "✅ 全部门禁通过"
```

### 5.2 三阶段门禁表

| 阶段 | 触发时机 | 执行内容 | 失败后果 |
|---|---|---|---|
| **本地** | 提交前 | `tools/verify.sh` | 不得提交 |
| **提交时** | `git commit` | `dotnet format --verify-no-changes` + build | 拒绝提交 |
| **审查时** | 发起审查 | 全量 test + `--smoke` | 不进入人工审查 |

### 5.3 建议引入的静态分析（见配套文件）

- **`.editorconfig`** —— 统一格式，消除 💭 级争议。
- **`Directory.Build.props`** —— 开启 .NET 分析器 + `TreatWarningsAsErrors` + `EnforceCodeStyleInBuild`。
  建议**先以降级方式引入**（关键规则设 `error`，其余设 `warning`），跑通全绿后再收紧。

## 6. 落地路线（按投入产出排序）

| 阶段 | 事项 | 预期收益 | 成本 |
|---|---|---|---|
| **P0 本周** | ① `git init` + 基线提交 + `.gitignore`<br>② 落 `.editorconfig`<br>③ 修 `配方存储` 原子写（🔴）<br>④ 审查清单上岗，L2/L3 改动必须走 PR | 解除"无版本控制"与"配置损坏"两大风险 | 半天 |
| **P1 下一步** | ⑤ `tools/verify.sh` 门禁脚本<br>⑥ `Directory.Build.props` 分析器（降级模式）<br>⑦ PR 模板 + 一页版检查清单打印贴墙 | 把可自动化项从人脑移交给工具 | 1 天 |
| **P2 稳定后** | ⑧ 接入 CI（GitHub Actions / 本地 runner）自动跑门禁<br>⑨ 补 `[Trait]` 分类，支持按改动范围选择性跑测试<br>⑩ 拆 `TeachService` / `RecipeService` 等超长文件<br>⑪ 覆盖率门禁（先只看通信层与 Business 层） | 长期防回归 | 持续 |

> **不要一次性全上。** 先做 P0，让团队在真实改动里用起来；用顺了再加 P1。
> 规则太多而没人执行，比没有规则更糟 —— 因为它会让人误以为质量有人管。
