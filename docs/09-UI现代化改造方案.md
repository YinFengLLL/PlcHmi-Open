## 〇、一句话结论

**这个项目做现代化改造的性价比异常高**——`Views/` 与 4 个对话框里 `#RRGGBB` 字面量出现 **0 次**，颜色 100% 走 `StaticResource`。也就是说，"换气质"这件事有 60–70% 可以在 `Themes/` 两个文件里完成，页面几乎不用动。

反过来，**真正的短板不是配色，是"骨架与生命感"**：全站 `VisualState` 0 处、`Views/` 下 `Storyboard` 0 处、窗口是系统默认标题栏、侧栏是白色平面列表。参考图之所以"现代"，靠的是**自绘窗框 + 深色壳层 + 主视觉区 + 卡片动效**这四件事，不是颜色本身。

## 二、设计方向

### 2.1 定调：深蓝工业 · Fluent 现代化（推荐）

参考图是「暗壳 + 青绿渐变内容区」。**不建议照搬青绿**：在工控语境里绿色承担"运行正常"的语义（本项目 `SuccessBrush #15803D` 正在做这件事），拿它当大面积背景会持续制造"一切正常"的错觉，属于语义污染。

推荐方案：**保留深蓝品牌锚点，把"壳层"整体压深，内容区保持浅色高可读，用渐变/圆角/动效制造现代感。**

- 壳层（顶栏 + 侧栏 + 底栏）：`#071A38 → #0B2A5B` 纵向渐变，统一为一个连续色域
- 内容区：`#F4F7FB → #EAF1FA` 极淡对角渐变（有纵深但不抢信息）
- 主视觉（首页 Hero / 关键卡）：`#0B3D91 → #1E88E5` 品牌蓝内渐变
- 圆角：卡片 8 → **12**，控件 6 → **8**，Hero 16，胶囊 999
- 动效：快 150ms / 基准 250ms / 慢 400ms，缓动统一 `CubicEase(EaseOut)`，**不用回弹**——工控界面回弹读起来"不严肃"

> **为什么内容区不做深色**：车间强光下深色底反光更严重、可读性反而下降，且现有 22 条 WCAG 校验全部基于白底。深色主题建议作为独立主题包后续提供（见 §6 决策项 4）。

### 2.2 壳层色板（新增令牌）

```xml
<!-- 壳层：顶栏/侧栏/底栏共用，形成连续色域 -->
ShellDeepColor          #071A38   侧栏底 / 底栏
ShellColor              #0B2A5B   壳层主色
ShellLightColor         #10377A   壳层高光端
ShellGradientBrush      LinearGradientBrush 0,0 → 0,1：#071A38 → #0B2A5B

<!-- 壳层上的文字与交互（替代现在只服务顶栏的 OnPrimary* 系列） -->
OnShellPrimaryBrush     #EAF2FF   壳层正文        ≥ 12:1
OnShellSecondaryBrush   #A9C2E4   壳层次要文字    ≥ 6:1
OnShellMutedBrush       #7A93B8   壳层弱化文字（版本号等，装饰性）
OnShellDividerBrush     #22FFFFFF 分隔线
OnShellHoverBrush       #14FFFFFF 悬浮底
OnShellActiveBrush      #26FFFFFF 选中底
OnShellAccentBrush      #4DA3FF   选中指示条 / 图标强调

<!-- 内容区纵深 -->
BackdropGradientBrush   #F4F7FB → #EAF1FA（135°）

<!-- 主视觉 -->
HeroGradientBrush       #0B3D91 → #1E88E5（135°）
```

⚠️ **门禁联动**
- 新增 token 必须同步登记进 `tools/check_contrast.py` 的 `CHECKS`；否则新色值无校验 = 白名单漏洞。
- **现有 token 色值一个都不许改**，否则会移动已通过的 22 条校验基准。
- `BackdropGradientBrush` 的**两端都要过 4.5:1**，并把 `BackgroundColor` 设为对比度**更差**的那一端——这样门禁才真的在约束渐变，而不是约束一个界面上不存在的纯色。

### 2.3 借鉴清单（按参考图元素拆解）

| 参考图元素 | 采用 | 落地方式 |
|---|---|---|
| 自绘标题栏 | ✅ | `WindowChrome` + 自绘三键（最小化/最大化/关闭） |
| 深色图标导航栏 | ✅ 改深色版 | 保留「图标 + 文字」横向布局——比纯图标栏更适合工控，新人不会迷路 |
| 页面 H1 + Hero 主卡 | ✅ | 首页新增 Hero 区 |
| 底部 Tile 快捷卡 | ⚠️ 变体 | 不放在首页（见 §2.4），改造为示教页 / 机种页的入口卡 |
| 青绿渐变背景 | ❌ | 语义冲突（见 §2.1） |
| 大面积装饰插画 | ❌ | 工控信息密度优先；装饰只允许出现在 Hero 与空状态 |
| 卡片悬浮阴影 | ⚠️ 变体 | WPF `DropShadowEffect` 以软件渲染为主，列表里挂阴影会掉帧 → **用"边框亮起 + 上移 2px"替代浮动**（`Palette.xaml` 已有此红线，继续保持） |

### 2.4 三条"不抄"的硬理由

1. **Tile 快捷卡不能取代 RunView 的四个大按钮。** 启动 / 停止 / 复位 / 报警清除是安全关键操作，必须保持"实心色块 + 大触控面积"。卡片化会削弱可感知性——参考图里那几个 Tile 是文档导航，点错了没有代价。
2. **不做数值动画。** 轴坐标、节拍、产量这些数字**禁止补间过渡**：中间帧会显示设备从未处于过的值，操作员按它做判断就是事故。允许动画的只有"表示进度/状态"的视觉容器（进度条宽度、指示灯亮度）。
3. **不做全屏渐变 + 玻璃拟态。** 车间强光 + 低端工控机，纹理与半透明会同时牺牲可读性与帧率。

## 五、三条红线

1. **安全关键操作的视觉权重不许降低。** 启动/停止/复位/急停保持"实心色块 + 大字重 + 大触控面积"，"卡片化""玻璃化""弱描边化"一律不适用于它们。
2. **数值显示不许做补间动画。** 只允许对进度条、指示灯亮度这类"表示"做动画。理由见 §2.4。
3. **新增颜色必须同步登记校验。** 否则 `check_contrast.py` 会从"约束"退化成只保护旧色值的摆设。

## 六、决策点

### 6.1 本轮已定（2026-09-17 实施）

| # | 决策 | 结论 | 依据 |
|---|---|---|---|
| 1 | 自研 vs 引入 WPF UI 库 | **自研** | 项目已有 54 个自绘图标 + 完整令牌体系 + 37 条对比度校验；引入库意味着推翻 `Themes/`、与中文标识符规范冲突，且其默认配色仍需改写 |
| 2 | 壳层深浅 | **深色壳层 + 浅色内容区** | 车间强光下深底反光更严重；且现有全部 WCAG 校验基于白底 |
| 3 | 卡片圆角 | 8 → **12** | 控件 6 → 8，新增主视觉 16 / 胶囊 20 |
| 4 | 深色主题包 | **本轮不实现**，仅令牌分层 | 需重算全部对比度，工作量翻倍 |
| 5 | Hero 渐变端点 | **`PrimaryDark → Primary`**，不是 `Primary → PrimaryLight` | 渐变上文字按**更亮端**核算：取 PrimaryLight 做亮端时次级文字只有 3.15:1，12px 正文直接跌破 4.5；改用 Primary 后最差 5.51:1 |

## 七、结论

改造的**技术杠杆在 `Themes/`，观感杠杆在 `MainWindow.xaml`**：

- 只改 `Palette.xaml` → 全局气质变化（零页面风险）
- 加上 `MainWindow.xaml` 的窗框与侧栏 → 达到参考图 60% 的观感
- 再加动效与首页 Hero → 达到 90%

建议按 P0 → P1 先走，跑完 `verify.ps1` 出 8 张截图做一次人工评审，再决定 P2 之后的节奏。

### 8.2 实施中修正的两处方案错误

1. **`WM_GETMINMAXINFO` 钩子不需要写。** 方案 §T1 把它列为必做（约 30 行 P/Invoke），实际排查后确认该坑只影响「没有 WindowChrome」的组合；挂了 WindowChrome 后 WPF 自己处理。加了反而有叠加风险，故不写。已在 `MainWindow.xaml` 留注释说明，避免后来人重走一遍。
2. **页面入场不动 `RenderTransform`。** 方案原写「淡入 + 上移 12px」。统一设 `RenderTransform` 只能走 `Setter`，而 Setter 里的 Freezable 会被冻结并在实例间共享，动画一跑就抛「无法在冻结对象上做动画」。为一个 12px 位移把 `RenderTransform` 铺到 8 个页面不值得，改为**只做淡入**。

### 8.3 顺带修掉的两个既有缺陷

1. **报警页两个滚动区被 DockPanel 停靠成左对齐。** `DockPanel` 里未写 `Dock` 的子元素默认 `Dock="Left"`，宽度收缩到「期望宽度」。列表为空时表现为空状态贴左，有数据时数据行可能与表头对不齐。已改为两个 `ScrollViewer` 叠放于同一层 `Grid`。
2. **进度条空轨几乎不可见。** 空轨用 `PrimarySoftBrush` 在白卡上与底色同色，进度为 0 时整条「消失」，看起来像渲染坏了。已改用 `OffBrush`。

**为什么该删**：那条纵向渐变在 62px 高的顶栏上根本看不出过渡，却让顶栏、侧栏、底栏三块底色"各自差一点"，拼在一起反而像没对齐。渐变要成立需要足够的面积与明度跨度，工业界面的壳层两者都没有。

### 9.2 IO 页新增「一栏 X 区 / Y 区」

**功能**：在 X 或 Y 区末尾追加一栏点位（默认 8 个），编号按八进制自动递增（X0–X27 之后是 X30–X37，不是 X28），随即写回 `io-points.json` 并重建采集计划。管理员专属（新权限 `权限.编辑IO点位`）。

**关键链路结论**（决定了实现可以很薄）：IO 点位**不经过标签体系**，轮询引擎编译读取计划时直接用点位代码解析地址（`PollingEngine.准备方案列表` 每次都从 `表格` 现取）。因此**运行时追加点位后调用 `异步重建方案列表()` 即可参与采集，不需要重启程序**。

| 层 | 改动 |
|---|---|
| `权限` | 新增 `编辑IO点位 = 1 << 11`，仅授给管理员 |
| `IO点位服务接口` | 新增 `预览下一栏(前缀)`、`异步新增一栏(前缀)` |
| `IO点位服务` | 八进制递增、越界整栏拒绝（不做部分写入）、维护 `元.输入/输出数量`、原子落盘 |
| `IO视图模型` | 注入用户服务与轮询引擎；权限随登录切换；确认框展示编号范围 |
| `IoView` | 工具条新增两个入口按钮，仅管理员可见 |
| `IoPointZoneTests` | 新增 5 项服务层测试（空表 / 八进制对齐 / 两侧互不影响 / 预览不改数据 / 越界拒绝） |

**两个易错点，已写进代码注释**：
1. 编号递增必须按八进制 —— `X27` 的序号是 23 不是 27，下一栏起点是 24（八进制 30）。测试 `新增一栏应按八进制对齐到下一个分组` 专门守这条，并顺带断言新编号能被 `汇川地址解析器` 接受（否则轮询编译时会**静默跳过**，点位显示正常却永远读不到）。
2. 调用顺序必须"先改表落盘、再重建计划"。反过来先重建等于白做；改表不重建，新点会显示在界面上却读不到状态——比不显示更糟。

**已知边界**：编号上限沿用汇川 X/Y 编址的 1023（八进制 1777）。`汇川地址解析器` 没有把这个数暴露成公共常量，`IO点位服务` 里持有一份副本并注明两处必须一起改 —— 这是已知的技术债，不是疏忽。
