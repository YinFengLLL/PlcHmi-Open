## 二、两者的分工（别混淆）

- **`Directory.Build.props`** 管**编译属性**：语言版本、分析器总开关、哪些规则升级为 error
- **`.editorconfig`** 管**代码风格**与**单条分析器规则的 severity**

要调某条规则的松紧 → 改 `.editorconfig`；
要开关整套分析器 → 改 `Directory.Build.props`。

## 三、三条关键规则的处理（各不相同，不要一刀切）

| 规则 | 含义 | 现状 | 依据 |
|---|---|---|---|
| `CA1849` | 异步方法内调用同步阻塞 API | **warning** | 2026-09-10 修净 4 处：`报警定义服务` / `手动元件服务` / `参数表格服务` / `用户服务` 的 `异步初始化` 里，同步的 `JsonSerializer.Deserialize` 改为 `await ...DeserializeAsync` |
| `CA2000` | 未释放 `IDisposable` | **warning** | 2026-09-10 修净 3 处：测试里 `虚拟PLC设备` 未释放。**注意它实现的是 `IAsyncDisposable`，必须写 `await using`**，写 `using` 会直接编译失败（CS8418） |
| `CA1031` | 不要捕获通用异常类型 | **suggestion（刻意保持，勿提升）** | 全项目 198 处命中，且绝大多数是**正确**的，详见下节 |

### 为什么 CA1031 不提升为 warning

这是本文最值得记住的一条。

把 198 处 `catch (Exception ex)` 收窄成 `catch (IOException)` 这类"精确捕获"，
在工控场景下**是错的**。现场环境比开发环境恶劣得多，会遇到开发期想不到的异常类型
（驱动层抛的、第三方库抛的、断电导致的半截状态）。收窄之后，这些异常会**穿透到顶层直接崩进程**——
对无人看守的触摸屏来说，这比"宽泛捕获后继续跑"严重得多。

所以本项目采取：**宽泛捕获 + 必须记录日志 + 必须有兜底**，规则只留在 IDE 提示级别。

## 四、防回归：升级为 error 的规则

`Directory.Build.props` 中：

```xml
<WarningsAsErrors>$(WarningsAsErrors);CS8600;CS8602;CS8603;CS8618;CA2000;CA1849</WarningsAsErrors>
```

选这些的理由：

- `CS8600 / CS8602 / CS8603 / CS8618` 可空性 —— 现场表现就是 `NullReferenceException`，属于"一出现就是缺陷"
- `CA2000` / `CA1849` —— 资源泄漏与 UI 线程阻塞，同上

这些规则在启用时刻的命中数均为 **0**，因此不会让现有构建变红。

**刻意没有做全量 `TreatWarningsAsErrors`**：那会逼着团队为了"先让它绿"去批量写
`#pragma warning disable`，比保留警告更糟。而 `tools/verify.sh` 里的 `-warnaserror`
已经提供了"提交前必须 0 警告"的强约束——两者配合，效果一致且不会逼人作弊。

## 五、门禁命令

```bash
dotnet build PlcHmi.slnx -warnaserror   # 任一警告即失败
dotnet test  PlcHmi.slnx                # 198 个测试
bash tools/verify.sh                    # 一条命令跑完 build + test + 界面自检
```
